3. Static Audit Findings Incorporated 
The static audit confirms the current product has deep functional value but also structural debt. The rebuild must 
preserve behavioral contracts while refusing to preserve the old code shape. 
3.1 Current Scale and Risk 
 Approximately 700 API operations across 58 route modules. 
 Approximately 45,000+ backend route lines and 91,000+ frontend page/component lines. 
 445 Pydantic model classes/enums. 
 1,127 tracked files, including 341 historical test-report artifacts. 
 159 backend test files, most depending on a live backend URL. 
 Zero frontend test files. 
 Primary rebuild risk: losing undocumented behavioral contracts connecting orders, pricing, production, portals, 
webstores, payments, payroll, and legacy records. 
3.2 Architecture Problems the Rebuild Must Not Copy 
 server.py must not own pricing logic, tenant routes, middleware, router registration, CORS, startup behavior, and 
lifecycle all together. 
 Routes must not directly query and mutate MongoDB as their normal pattern. 
 Route/service modules must not import dependencies back from server.py. 
 Orders/tickets and legacy jobs/job-items must be reconciled through a migration plan, not kept as competing active 
workflows forever. 
 Plans, tiers, founders status, and entitlements must be normalized into one plan/entitlement system. 
 Pricing defaults, configuration, templates, snapshots, and legacy fields must be mapped into canonical pricing 
behavior without losing historical snapshot meaning. 
 Frontend routes must use lazy loading/code splitting instead of importing every public, portal, admin, and 
authenticated page at initial bundle construction. 
 Large pages such as PricingCalculator, PricingFoundation, Webstores, and Dashboard must be decomposed into 
focused components and domain hooks/services. 
 AppContext must be narrowed. Do not expose a giant non-memoized object with dozens of API functions and broad 
global state. 
 Tier and Plan providers must not duplicate subscription-feature responsibilities. 
 Dashboard/productivity queries must not load thousands of records repeatedly into Python memory. 
 N+1 queries must be eliminated before release acceptance. 
 Index migrations must be managed and run consistently for every high-volume collection. 
 Object storage must not use blocking synchronous calls inside async request paths. 
 Large files, images, PDFs, audio, and generated artifacts must not be stored or returned as base64-heavy Mongo/API 
payloads. 
 Backup/restore must be streaming and transactionally safe, not full-tenant memory snapshots. 
 Background scheduling must not be process-local inside the API process if multiple workers/replicas can exist. 
 Authorization must be centralized and consistently used by route and service layers. 
 Production CORS must not fall back to allow-all regex behavior. 
 Test coverage must move from live-URL smoke tests to deterministic unit, service, API integration, browser, 
permission, and tenant-isolation tests.

1. Executive Decision Summary 
This document replaces the mixed rebuild notes with one accepted plan. The current main app remains the approved 
product-behavior reference. The rebuild may replace code, collections, route names, and component structure, but it 
must preserve approved features, fields, defaults, calculations, workflows, and design behavior unless an explicit

 The final app shell must exist from the beginning: Home / Global Command Center, Operations, Business, 
Productivity, AI Hub, Settings, notifications, global search, global + Create, and contextual Office-style ribbon. 
 Emergent's "Know from Day 1" rebuild guidance is accepted as authoritative implementation guidance where it 
conflicts with the broader early roadmap notes. 
 Webstores are a protected approved area. They are not automatically delayed to a late release. Existing approved 
webstore behavior should be rebuilt early unless a specific feature depends on unfinished infrastructure such as 
production Stripe Connect, inventory reservations, or external integrations. 
 Canonical shared models must be used for tasks, notes/comments, messages, calendar events, notifications, files, 
activity timelines, and audit events. Modules must not invent duplicate versions of these concepts. 
 Money must be stored as integer cents. Quantities must use explicit units. Authoritative calculations must live in 
deterministic backend services, not AI and not the frontend. 
 Routes must stay thin. Domain services and repositories own business logic and database access. server.py is only 
app initialization and router registration. 
 Every protected area gets a written behavior specification before rebuilding. That is not optional. This is how we avoid 
accidentally replacing approved behavior with something cleaner but worse, because apparently humans keep 
doing that.

7. Canonical Shared Models 
 
8. Data Model Principles 
 Every tenant-scoped collection includes tenant_id and required tenant indexes. 
 Every record has a stable uuid id and never exposes raw MongoDB _id in API responses. 
 Use datetime.now(timezone.utc).isoformat() or a consistent timezone-safe equivalent. Do not use naive datetimes. 
 Human-readable numbers use tenant-scoped atomic counters: ORD-0001, INV-0001, QUO-0001, TKT-0001, PO-
0001. 
 Money fields use integer cents. Examples: subtotal_cents, tax_amount_cents, total_cents, unit_price_cents, 
amount_paid_cents. 
 Quantities include explicit units and dimensions where relevant: sq_ft, linear_ft, inch, roll_length_inches, 
sheet_width_inches, etc. 
 Important mutations create audit events and user-facing activity events where appropriate. 
9. Orders, Order Items, and Job Tickets 
Use one canonical Order model. Do not rebuild a separate legacy Job model. Commercial work and production 
execution are related but not the same thing. 
Order 
└── OrderItem (1 or more commercial line items) 
    └── JobTicket (created only when production_required = true) 
        └── ProductionTask / Canonical Task links as needed 
9.1 Order 
 Order stores customer_id, order_number, source, order_type, due date, notes, special instructions, totals, deposit, 
tax, balance display, and activity. 
 Order totals are calculated by backend services from order items, discounts, taxes, deposits, and payments. 
 Order.status is service-derived from order item/job ticket state, except approved lifecycle exceptions such as On 
Hold, Cancelled, Archived. 
 Webstore orders set is_webstore_order, webstore_order_id, and webstore_name at creation. Do not retrofit these 
later. 
9.2 OrderItem 
 OrderItem owns sold/commercial specifications: product type, description, quantity, dimensions, material choice, 
unit price, line total, pricing snapshot, artwork status, and override reason where applicable. 
 OrderItem includes production_required: true/false. Physical production items default true. Fees, deposits, delivery 
charges, design-only charges, and administrative items default false. 
 OrderItem pricing snapshots freeze the pricing foundation/config used at quote or order time so later changes do not 
rewrite history. 
9.3 JobTicket 
 JobTicket owns production execution: stage, priority, assignee, production notes, install notes, packaging notes, 
rework notes, artwork files, proof status, material requirements, and activity. 
 A JobTicket is generated automatically when a production_required OrderItem is created or converted from quote to 
order.

 JobTicket tabs: Overview, Artwork, Proofs, Materials, Notes, Activity. 
 Production stages are tenant-configurable in Settings > Production. Do not hardcode them in the board. 
10. Customers, Quotes, Pricing, and Invoices 
10.1 Customers 
 Customer records include display name, company name, email, phone, billing/shipping addresses, customer type, 
tax exemption, preferred contact method, tags, notes, files, and active/archive state. 
 Customer lifetime value is computed on read from paid invoices. Do not store it as a mutable field. 
 Customer portal routes are separate public/portal flows with explicit allowlists, not internal APIs with a prettier login 
screen. 
10.2 Quotes 
 Quotes include quote number, customer, status, expiration, line items, subtotal, tax, total, notes, pricing snapshot, 
and converted_order_id. 
 Quote to Order conversion is idempotent and creates OrderItems and JobTickets for production_required items. 
 Public quote acceptance uses signed token links with expiration and audit/activity events. 
10.3 Pricing Foundation and Calculator 
 Pricing Foundation lives in Settings > Pricing and stores category defaults, materials, labor, markup, overhead, 
waste, minimums, and quantity breaks. 
 Pricing Calculator is its own tool and also appears as a global quick action and inside quote/order item workflows. 
 All formulas are pure deterministic functions: calculatePrice(inputs, foundationConfig) returns a breakdown and 
price with no side effects. 
 Calculator should work with or without a selected customer for fast phone quoting. 
 Quantity breaks are per-category, not global. 
 Manual price overrides require a reason and create an audit event. 
10.4 Invoices and Payments 
 Invoices are immutable billed snapshots generated from orders or manually created where allowed. 
 Invoice balance is computed from total_cents minus sum of payment transactions. Do not store balance as a free-
edit mutable field. 
 Partial payments and refunds are stored in payment_transactions. 
 Public payment links use signed or random stored tokens, not exposed invoice IDs. 
 Overdue status is computed from due date and payment state; scheduler sends reminders but does not blindly 
mutate status without service rules.

13. Team, Timeclock, Schedule, and Payroll 
 Team schedule, timeclock, and payroll rules are protected behavior areas and must be specified before rebuild. 
 Employee scheduling should support multi-employee day/week scheduling from one board, not one employee

14. Inventory and Purchasing 
Inventory and purchasing are protected behavior, but the accepted sequencing keeps them after Orders, JobTickets, 
Pricing, Production, Tasks, Notifications, and Activity are stable. Webstores do not need to wait for inventory unless 
using stocked-product reservations. 
 InventoryItem is the catalog record. InventoryLot is the physical batch. InventoryTransaction is the immutable 
ledger. 
 Tracking methods include quantity, roll, sheet, remnant, pack, board/case as needed. 
 Balances are computed from ledger/lots: on hand, reserved, available, incoming, shortages, value. 
 Never mutate quantity_on_hand directly without a transaction record. 
 Material requirements link JobTickets to InventoryItems and can become reserved, pulled, consumed, shortage, 
returned, or waste. 
 Shortages surface in Action Required and can become draft purchase order lines. 
 PO receipt creates inventory lots, receipt transactions, updates incoming/on-hand status, and resolves linked 
shortages. 
 Supplier APIs, live comparison, automatic ordering, AI purchasing recommendations, and webstore inventory 
reservations are later dependencies, not MVP blockers. 
15. Portals, Communications, and Notifications 
 Each portal is a separate security boundary: Customer Portal, Employee Portal, Webstore Owner Portal, Partner/B2B 
Portal, Public Token Pages, Platform Admin Portal. 
 Customer/order communications belong in Operations. Team/internal messages belong in Productivity. Platform 
support/community messages belong in AI Hub. 
 Email templates should be defined centrally for proofs, invoices, overdue invoices, payment received, order

16. AI Hub and Automation 
 AI Hub exists from the beginning for product identity, help, documentation, prompt library, bug reports, feature 
requests, roadmap, and release notes. 

===== PAGE 13 =====
 Active AI tools wait until deterministic workflows and guardrails are ready. 
 AI can draft emails/texts/product descriptions/documents, summarize, explain, and suggest only inside permission-
filtered context. 
 Mutating actions require explicit review with preview, sources, assumptions, affected records, and predicted 
impact. 
 AI cannot directly approve purchase orders, alter inventory, submit supplier orders, issue refunds, change selling 
prices, bypass permissions, or block manual workflows. 
 AI credit charging must be idempotent and tied to completed actions, not failed attempts.
