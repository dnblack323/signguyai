Prepared from COMBINED.pdf rebuild notes and corrected Day 1 meaning 
 
Core resolution rule: “Day 1” means Emergent’s “what it wished it knew from Day 1” rebuild specification, 
not Release 1. When Day 1 guidance conflicts with the Early Plan, Day 1 should usually win, especially 
where it protects app architecture, known approved behavior, webstores, pricing, orders, dashboard, 
ribbon navigation, permissions, and data models. Exceptions: tenant isolation, security, payment safety, 
deterministic money/payroll/inventory math, and explicit owner-approved behavior always override 
generic suggestions. 
 
How to use this document: Each conflict is numbered. Each option is lettered. You can respond with choices like “1A, 2B, 
3C.” Labels show where an option came from: [DAY 1], [EARLY PLAN], [ROADMAP], [USER CORRECTION], or 
[RECOMMENDED SYNTHESIS]. 
Executive Summary 
The rebuild notes mostly agree on one big direction: preserve approved current-app behavior, rebuild cleaner architecture, and 
establish the final app shell early. 
The largest strategic conflict is webstores. One roadmap draft defers active webstores to Release 6, but the Day 1 spec treats 
webstores as a core value loop and includes detailed webstore architecture. Since your webstores are mostly how you want 
them, the recommended resolution is to keep active webstores in the early rebuild scope after a protected webstore behavior 
spec is approved. 
The second biggest conflict is architecture detail: some model examples use float money fields, direct route DB access, and 
always-created JobTickets, while the stronger architecture rules require integer cents, service/domain boundaries, and 
canonical ownership. 
The final spec should not blindly follow the release roadmap where it delays already-approved or already-working features. It 
should follow the Day 1 rebuild spec and protected-behavior rule first.

preserving avoidable contradictions.

Use this wording in the final rebuild prompt/spec: 
Webstores are not a future-only idea in the rebuild. The existing webstore behavior is a protected area and is mostly approved. 
The rebuild must preserve the approved webstore setup flow, store types, owner invite/onboarding behavior, product catalog 
behavior, public storefront expectations, order synchronization, and dashboard/ribbon placement unless the owner explicitly 
approves a change. 
The Day 1 Webstores specification is the default source of truth for webstore architecture. The Early Plan may still be used for 
dependency sequencing, but it must not downgrade approved active webstore behavior into a shell-only placeholder. 
If any webstore capability depends on an unfinished underlying service, implement the approved UI and data contracts early, 
then feature-flag only the unsafe dependent action. Examples: advanced inventory reservations may wait for inventory, but 
store setup, products, fundraiser/B2B modes, owner portal structure, and canonical order sync should not be delayed simply 
because a roadmap draft placed ecommerce later. 
Stripe Connect and checkout must be implemented only with webhook verification, idempotency, tenant isolation, 
reconciliation, and failure recovery. This is not a reason to defer webstores as a whole; it is a reason to implement payment 
safety correctly.

Final Conflict Resolution Rules to Insert Near Top of Rebuild Spec 
1. Emergent Day 1 guidance is the default source of truth when it conflicts with the Early Plan, because it represents what the 
original builder wished it knew before implementation began. 
2. Protected approved behavior wins over generic release sequencing. Protected areas include Pricing Foundation, 
product/item categories, pricing defaults, webstores, dashboard layout, ribbon navigation, team/payroll, inventory/purchasing, 
document library, portals, Wrap Command Center, and AI guardrails. 
3. The current main app is the product-behavior reference, not the code-structure reference. Approved behavior, fields, 
calculations, defaults, workflows, and design behavior must be preserved unless explicitly changed by the owner. 
4. Webstores are an early active scope item, not automatically a late Release 6 item, because the current webstore behavior is 
mostly approved. Only unsafe dependencies may be feature-flagged or staged. 
5. Final app surface appears early: Home/Global Command Center, Operations, Business, Productivity, AI Hub, global search, 
global create, notifications, settings, contextual ribbon, and permission-filtered navigation. 
6. Architecture must use canonical shared concepts: Order, OrderItem, JobTicket, Task, Note/Comment, 
Message/Conversation, CalendarEvent, Notification, File, AuditEvent, and ActivityTimeline. 
7. Deterministic business logic controls pricing, inventory, payroll, accounting, payments, taxes, refunds, and approvals. AI 
may draft or suggest later, but it may not silently mutate money, inventory, approvals, or supplier actions. 
8. Money is stored as integer cents. Float examples in drafts are not final schema decisions. 
9. Public portals and token pages must use separate security boundaries and allowlisted data. Internal cost data must never 
leak to customer, employee, webstore-owner, partner, or public-token surfaces. 
10. Routes must not become giant business-logic files. Routes handle auth/request/response; services and repositories own 
business rules and persistence.
