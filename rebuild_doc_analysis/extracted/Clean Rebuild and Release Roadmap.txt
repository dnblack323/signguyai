# SignGuyAI Clean Rebuild and Release Roadmap 
 
## Authoritative Direction 
 
The current `main` application is the product-behavior reference. The rebuild may replace its code and 
data structure, but it must preserve approved features, ﬁelds, defaults, calculations, workﬂows, and 
design behavior. 
 
The rebuild will use staged releases, but it will **not** hide the future app structure until later releases. 
The ﬁnal navigation, workspaces, routes, permissions, data ownership, and page patterns must be 
established at the beginning. Later releases deepen those stable surfaces. 
 
## Final App Surface Rule 
 
Every major ﬁnal workspace and module must exist from Release 1 in one of these states: 
 
- Working minimal feature 
- Read-only dashboard 
- Setup placeholder 
- Clearly labeled coming-soon page 
- Feature-ﬂagged internal preview 
- Module shell documenting its target behavior 
 
This prevents repeated navigation rewrites, route churn, permission rewrites, and layout restructuring. 
 
Placeholder modules must never pretend to work. They must clearly show their status, planned 
capability, and dependencies.

## Clean Architecture Rules 
 
1. Build a modular monolith with one deployable frontend and backend and enforced domain 
boundaries. 
2. Use one canonical `Order`; do not recreate a separate legacy `Job`. 
3. Use `OrderItem` for commercial line items and `JobTicket` for production execution. 
4. Use canonical tasks, notes, messages, calendar events, notiﬁcations, ﬁles, and activity events. 
6. Put all tenant-scoped access behind shared authorization helpers. 
7. Keep deterministic pricing, inventory, payroll, and accounting calculations outside AI. 
8. Add external integrations only after their manual workﬂow works. 
9. Keep every portal isolated from internal APIs and internal cost data. 
10. Use feature ﬂags and staged tenant rollouts for every major capability. 
11. Require migrations, rollback plans, monitoring, and acceptance tests for every release. 
12. Do not recreate giant route modules or multi-thousand-line page components.

## 1. App Overview 
 
**SignGuy AI** is a multi-tenant SaaS operating system for sign shops. One account = one sign shop 
(tenant). A single platform owner (platform_creator) manages all tenants. 
 
**Core value loops:** 
- Take a customer job → produce it → invoice it → get paid 
- Run a webstore → customers self-order → auto-enters production queue 
- Price jobs accurately using conﬁgured material + labor costs 
- Track materials from purchase order → stock → job consumption 
 
**User types:** 
| Role | Who | What they see | 
|---|---|---| 
| `platform_creator` | You (the SaaS owner) | Everything across all tenants | 
| `platform_admin` | Your support staƯ | All tenants, no billing | 
| `owner` | Sign shop owner | Full access to their tenant | 

===== PAGE 18 =====
| `admin` | Shop manager | Full operational access, no billing settings | 
| `staƯ` | Employees | Assigned work, timeclock, limited views |

## 2. Tech Stack Decision 
 
| Layer | Choice | Why | 
|---|---|---| 
| Frontend | React + Tailwind CSS + Shadcn/UI | Component library already built, CSS variables for 
theming | 
| Backend | FastAPI (Python) | Async, clean routing, Pydantic validation | 
| Database | MongoDB (Motor async) | Flexible schemas per tenant, no migrations for new ﬁelds | 
| Auth | JWT (HS256) | Stateless, works across preview + production | 
| Payments | Stripe (direct) + Stripe Connect (webstores) | Two separate integrations | 
| Email | SendGrid | Transactional templates | 
| AI | Emergent LLM Key → OpenAI / Claude / Gemini | Single key, no per-model API key management | 
| File Storage | Object storage (S3-compatible) | Artwork ﬁles, proof PDFs, generated documents | 
| Process Manager | Supervisor | Frontend :3000, Backend :8001 |

    email_service.py       # All SendGrid calls

class Permission(str, Enum):

    ORDERS_DELETE = \"orders:delete\"

    admin: [all except billing/settings:delete] 
    staƯ: [view-only + timeclock + assigned work] 
 
def has_permission(user: UserInDB, permission: Permission) -> bool:

## 13. Inventory & Materials 
 
### Data model 
``` 
InventoryItem       (the catalog record — \"Cast Vinyl 54-inch Roll\") 

===== PAGE 29 =====
└── InventoryLot    (a physical batch — \"Roll #3, received 2025-06-01, 1500ft remaining\") 
    └── InventoryTransaction  (ledger entries — receipts, pulls, waste, adjustments) 
``` 
 
### TrackingMethod 
```python 
\"quantity\"   # simple count (hardware, grommets) 
\"roll\"       # width_inches + remaining_length_inches 
\"sheet\"      # sheet_width_inches × sheet_height_inches × quantity 
\"remnant\"    # oƯ-cut piece with speciﬁc dimensions 
\"pack\"       # quantity in pack_size units 
``` 
 
### Balance calculation (always computed from ledger) 
```python 
on_hand    = sum(quantity_on_hand for lot in lots where is_active) 
reserved   = sum(reserved_quantity for lot in lots) 
available  = on_hand - reserved 
inventory_value = sum(qty × unit_cost for lot in lots) 
``` 
**Never mutate `quantity_on_hand` directly** — always insert a transaction, then update the lot. 
 
### Material requirements → job ticket link 
```python 
{ 
  ticket_id: uuid, 
  inventory_item_id: uuid, 
  required_quantity: ﬂoat, 
  required_width_inches: ﬂoat | None, 
  required_length_inches: ﬂoat | None, 
  status: \"open|reserved|pulled|consumed|shortage\" , 
} 
``` 
 
### Shortage handling 
If `available < required_quantity`, create an `InventoryShortage` record and link it to the requirement. 
Shortages surface in the dashboard \"Action Required\" card and can be converted into a PO line item. 
 
**Know from day 1:** 
- `InventoryItem.pricing_material_key` links to a Pricing Foundation material key — this is how cost ﬂows 
from purchasing to pricing automatically 
- Roll tracking: when a roll is partially consumed, create a new \"remnant\" lot from what's left 
- Cycle count adjusts the lot's `quantity_on_hand` and inserts a `cycle_count_adjustment` transaction

 SignGuyAI Clean Rebuild and Release Roadmap 
EARLY PLAN 
 Purpose 
This document treats the current `main` branch as the target product reference. The goal is not to copy its current 
code structure. The goal is to recreate the same useful product capabilities through a faster, cleaner, dependency-
driven build sequence. 
 
The current application is broad and valuable, but it contains several generations of implementation: 
- Legacy Jobs alongside Orders and Job Tickets 
- General Tasks, Production Tasks, production timelines, and uniﬁed productivity views 
- Multiple billing, subscription, and payment paths 
- Large pages and route modules that own too many responsibilities 
- Features added before their underlying workﬂow had stabilized 
 
The rebuild should preserve the target behavior while replacing these overlaps with one canonical model per 
business concept. 
 
 Inspection Findings 
The current repository demonstrates the complete product direction, but its structure also explains why additional 
changes have become increasingly . 
 
- The backend currently registers roughly 58 route modules through a `server.py` ﬁle that is more than 4,600 lines 
long. 
- The frontend contains roughly 133 page ﬁles. Several major pages are over 1,000 lines, and the largest are over 
2,000 to 3,000 lines. 
- There are roughly 159 backend test ﬁles, but many are iteration-speciﬁc regression ﬁles or external smoke tests 
rather than a single dependable release suite. 
- Core concepts overlap: legacy Jobs coexist with Orders and Job Tickets; several task and production systems 
feed a uniﬁed productivity layer; billing and payments have multiple generations. 
- High-value external systems include Stripe, Stripe Connect, SendGrid, OpenAI/Emergent integrations, 
Meta/Facebook, SMS, object storage, and scheduled jobs. 
- The current inventory and purchasing implementation is integrated with Orders, Job Tickets, Pricing Foundation, 
production material pulls, and role permissions. It should be preserved as the target inventory behavior. 
 
These ﬁndings support a staged rebuild that starts with canonical models and contract tests rather than a page-
for-page code port.

 Two Different Milestones 
 
** ** means a real sign shop can run its core order workﬂow with a small number of invited 
users. It does not need every SaaS growth, ecommerce, workforce, inventory, or AI feature. 
 
** ** means the product is safe to sell broadly. It requires production billing, 
support controls, tenant isolation veriﬁcation, reliable email, backup and restore, observability, and 
tested critical workﬂows. 
 
Do not confuse feature count with launch readiness. A smaller product with reliable workﬂows is more 
sellable than a larger product with uncertain money or data paths. 
 
 Build Rule 
1. Build a modular monolith ﬁrst. Keep one deployable backend and frontend, but enforce domain 
boundaries. 
2. Use one canonical `Order` model. Do not recreate a separate legacy `Job`. 
3. Use `OrderItem` for commercial line items and `JobTicket` for production work. 
4. Use one canonical task model with typed task sources and views. Do not create unrelated task 
collections for every module. 
5. Store money as integer cents and quantities with explicit units. 
6. Put all tenant-scoped access behind shared authorization helpers. 
7. Record important business changes as immutable audit events. 
8. Keep deterministic pricing, inventory, payroll, and accounting calculations outside AI. 
9. Add external integrations only after the manual workﬂow works. 
10. Keep public portals isolated from internal APIs and internal cost data. 
11. Use feature ﬂags and staged tenant rollouts for every major release. 
12. Every release must include migration, rollback, monitoring, and acceptance tests.
